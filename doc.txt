Goal:
Add clothing items with basic attributes (name, category, color, size, quantity, optional photo link).
Browse/search/filter items by attribute.
Edit/delete items safely (with undo or confirmation).
Authentication with username+password; user-private data silo.
Observability: basic metrics, error tracking, health checks.
Conversational AI assistant (MVP+): users can ask natural-language questions (e.g., "show my black hoodies in M"), and the assistant executes searches and summarizes results.

Planning:
Week 1: Planning/design complete, repo & CI setup.
Week 2: Backend slice (Clothing create/list) + DB indexes/seed; staging deploy.
Week 3: Frontend slice integrated; auth; observability baseline.
Week 4: Edit/delete, search/filters, assistant MVP (search + summarize), polish, canary to prod.


Design:
1. api planning:
    authentication: post /auth/login; post /auth/signup; post /auth/logout
    items: get /items; post /items; get /items/{id}; delete items/{id}
    assistant: post /ai/assistant
    For this API, we only send one combined message per request (which contains the whole needed context).
    (Update: rather than having an conversation database, we use single prompt + last 4-6 message
    implement conversation databse can be after application stablized)
    (for this api, we are handling one user message at a time, not the whole conversation,
    to make sure backend have the whole chat history, we need to create a conversation databse with conversation_id)
2. Data
    user:{_id, username, password(hased), email}
    cloth:{_id, user_id, name, type, color, size, season, description}
    (future: 
        conversation:{_id, user_id, title, create_at}
        message:{_id, conversation_id, content, user_id}
    )

    optimization: currently we are using ownerID to fetch all the clothes from the user;
    in future, when the database size increase, we can optimize it by
        1. adding index on ownerID(MongoDB uses a B-tree index internally to directly locate all documents with that ownerId — no scanning.)
        2. Instead of always pulling the full wardrobe, I’d expose a search-style tool that lets the AI request items by filters like color, type, or season. 
           That way, the database only returns a small subset of relevant clothes, which is both faster and cheaper for the LLM to process.
3. tool 
    the ai agent has access to the database and only get the cloth for the user
    rather than all clothes whether it is in the database or search online.
    (maybe later implment more tools)
